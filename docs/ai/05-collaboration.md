# 05 · 多人 / 多 AI 协同开发协议

本仓库会同时有人类开发者和多个 AI 代理（不同工具、不同会话）参与。AI 会话没有长期记忆、上下文会被压缩或中断，
所以**协作状态必须写在仓库里**：任务看板（[08-roadmap](08-roadmap.md)）、交接记录（[`docs/handoff/`](../handoff/)）、
架构决策（[`docs/adr/`](../adr/)）、提交历史。任何人（或任何代理）只看仓库就能接上工作。

## 1. 角色

| 角色 | 职责 |
| --- | --- |
| 负责人（人类） | 定优先级与业务口径、批准破坏性变更、合并 PR、处理代理之间的冲突 |
| 开发代理（AI / 人） | 认领任务、实现、测试、更新文档与看板、写交接 |
| 评审代理（AI / 人） | 按 §7 清单评审 PR，只提问题不直接改别人的分支（除非被要求） |

## 2. 任务生命周期

```
待认领 ──认领(登记负责人/分支)──▶ 进行中 ──▶ 待评审(PR) ──▶ 已完成
                │                    │
                │                    └─▶ 已暂停（必须有交接记录） ──▶ 被任何人重新认领
                └─ 依赖未满足 → 阻塞（写明阻塞原因）
```

规则：

1. **先登记再动手**：在 08-roadmap 的看板表格把任务改为 `进行中`，填写负责人（如 `claude 会话 016P…`、`codex`、`alice`）、分支、日期，作为单独的提交推送，让其他人尽早看到。
2. **一人一任务**：一个代理同时只持有一个 `进行中` 任务；需要切换时先把当前任务改为 `已暂停` 并写交接。
3. **超时回收**：`进行中` 超过 3 天没有提交，且负责人未回应，其他人可以在看板备注后接手（先读交接或分支）。
4. **任务太大就拆**：预计超过 1 天或跨 3 个以上模块的任务，拆成子任务（`T15a`、`T15b`）分别登记，避免长期大分支。
5. **完成**：合并后在看板标记 `已完成` 并写上提交 / PR 链接；新发现的工作以新任务卡加入待办，不要悄悄扩大当前任务。

## 3. 分支与合并

- 分支：`<负责人>/<主题>`；从最新主干创建，频繁同步主干（建议每天至少一次），**用 merge 同步，不要 rebase / force-push 别人的分支**。
- PR 要小（建议 < 800 行有效改动，生成文件与迁移除外）；PR 描述按 `.github/pull_request_template.md` 填写。
- 只有 CI 全绿 + 至少一位评审通过后才能合并；合并方式由负责人决定。
- 不推送到别人的分支；需要协作时在 PR 里留言或开新分支基于其分支工作。

## 4. 数据库迁移协同

迁移是最容易冲突的地方（Alembic 要求单一 head）。

- **一个 PR 最多一个迁移文件**；同一 PR 内多次改模型，就删掉旧迁移重新生成一个。
- 生成前先同步主干，在「停在主干 head」的干净库上 autogenerate（步骤见 [04-workflow §4](04-workflow.md#4-数据库迁移)）。
- 合并前如果主干出现了新迁移（`alembic heads` 出现两个 head）：**删除自己的迁移，基于新主干重新生成**（推荐）；
  或把自己迁移文件的 `down_revision` 改为主干最新 revision 后重新做两库验证。不要提交 `alembic merge` 产生的合并迁移，保持线性。
- 已经合并到主干的迁移**永不修改**，只能追加新迁移修正。
- 数据迁移（回填数据）写在迁移里时必须幂等，并在 PR 描述中说明对现有数据的影响。

## 5. 冲突热点文件（只做追加式最小改动）

| 文件 | 规则 |
| --- | --- |
| `backend/app/models.py` | 按字母序插入一行 import |
| `backend/app/main.py` | 在 router 列表末尾追加一行；import 放在同组字母序位置 |
| `backend/app/core/permissions.py` | 在对应分组末尾追加权限；新分组加在 `system` 之前；改 `PRESET_ROLES` 需负责人同意 |
| `backend/app/modules/system/settings_registry.py` | 按域分段追加，键名 `域.参数` |
| `backend/app/cli.py`（seed_demo） | 在函数末尾 `print` 之前追加独立的演示段落，带中文注释标题；不要改已有段落的数据 |
| `backend/tests/conftest.py` | 只追加 Factory 方法，不改已有方法签名 |
| `frontend/src/router/routes.tsx` | 在对应分组的 children 末尾追加；新分组需负责人同意（影响菜单结构） |
| `frontend/src/utils/dicts.ts` | 文件末尾追加新字典 |
| `frontend/src/components/common.tsx`、`DataTable.tsx`、`api/client.ts` | 公共组件：只做向后兼容的扩展（新增可选 props），改行为需在 PR 中说明影响面 |
| `alembic/versions/` | 见 §4 |
| `docs/ai/08-roadmap.md` | 只改自己任务所在的行；新任务追加到表尾 |

并行开发时，按**模块**划分负责人最安全；两个任务都要改同一个 service 文件时，先合并一个再开始另一个。

## 6. 接口契约

- 后端 schema 与前端调用必须在同一个 PR 中保持一致；前端类型多为 `Record<string, any>`，**改字段名要全局搜索前端**（`grep -rn "field_name" frontend/src`）。
- 破坏性变更（删字段、改语义、改 URL）需在 PR 描述中写明，并经负责人同意；门户 `/portal/*` 与连接器 DTO 被外部系统依赖，默认只能新增不能删改。
- 新的业务口径（如利润构成、状态流转）先写进 [01-domain](01-domain.md)，再改代码。

## 7. 评审清单

- [ ] 多租户：没有手写 `tenant_id` 过滤；跨租户查询显式 `skip_tenant_filter` 且有理由
- [ ] 权限：每个接口都有 `perm()` / 合适的依赖；按店铺数据有过滤；成本字段按权限隐藏
- [ ] 库存只经 `InventoryService`；并发场景有 `FOR UPDATE OF` 行锁
- [ ] 金额用 `Decimal`，没有 float 参与计算；币种 / 本位币处理正确
- [ ] 写操作有 `audit()`；事务边界正确（内部函数不提交，最外层提交；批量用 savepoint 隔离）
- [ ] 错误信息为中文且对用户有意义；没有吞掉异常
- [ ] 没有 N+1 查询（列表输出批量取关联数据）
- [ ] 迁移与模型一致、两库验证过、使用 batch 模式修改已有表
- [ ] 测试覆盖主流程 + 错误路径，两库通过
- [ ] 前端：antd v6 写法、权限按钮、加载 / 空状态、中文文案、无控制台报错
- [ ] 文档 / 看板 / 演示数据按需更新；没有提交密钥或真实数据

## 8. 交接（Handoff）

**什么时候必须写**：任务暂停、会话即将结束 / 上下文快用完、换人或换代理、被打断去做别的事。

**写在哪里**：`docs/handoff/YYYY-MM-DD-<主题>.md`（模板 [`templates/handoff.md`](templates/handoff.md)），并在看板对应行链接它。

**必须包含**：
1. 目标与范围（链接任务卡）
2. 当前状态：哪些文件已改 / 新增，**是否已提交、在哪个分支**；未提交的改动要逐个列出路径
3. 已验证什么（命令与结果）、**没验证什么**
4. 下一步（可直接照做的有序清单）
5. 风险、未决问题、需要负责人决定的事项

未完成的代码处理：
- 能通过 lint 与现有测试、但功能未完成 → 可以推送到**自己的分支**（不要合并），交接里注明。
- 不能保证不破坏现有功能 → 不要推送到共享分支；在交接里列出未提交文件，或推送到单独的 `wip/` 分支（需有权限）。

**接手的人**：先读交接 → `git status` / `git log` 核对现状 → 跑一遍「已验证」里的命令确认环境 → 从「下一步」开始 → 在看板把负责人改成自己。

## 9. 沟通

- 语言：文档、注释、UI、提交正文用简体中文均可；提交标题用英文祈使句。
- 汇报节奏：每完成一个子功能简短说明「做了什么、怎么验证的、下一步」；遇到阻塞立即说明原因与需要的帮助。
- **需要先问人类负责人的事**：业务口径不明确；删除或批量修改数据；破坏性接口 / 数据结构变更；引入新的外部服务或付费依赖；调整权限模型或菜单结构；任何不可逆操作。
- 不要为了让测试通过而删除 / 跳过测试，或放宽断言；发现测试本身错误时在 PR 中说明理由。

## 10. 多个 AI 并行的推荐分工方式

1. 负责人在 08-roadmap 中把大目标拆成按模块独立的任务卡，并写清验收标准与接口契约。
2. 每个代理认领一个任务，在独立分支开发；跨任务的共享改动（新权限、新字典、公共组件扩展）由先开始的一方提交并尽快合并，后者同步主干后复用。
3. 同一时间只允许一个任务包含迁移；其余任务如需模型改动，排队或与负责人协调顺序。
4. 每个代理完成后由另一个代理按 §7 评审；评审意见以 PR 评论形式给出，原作者修改。
5. 集成节奏：至少每天把已完成的任务合并一次，并在主干跑一次完整的浏览器冒烟（登录 → 各主菜单打开 → 关键流程）。
